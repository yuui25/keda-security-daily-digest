- 一番多いのは、前号に続いて **「検査する側と、実際に処理する側で解釈が違う」** 型だ。fastify (middie / express) はパスの正規化、Eclipse Ditto は「ヘッダは守ったがクエリパラメータは見ていなかった」、SiYuan は XFF の信頼、Jupyter MCP はルートごとの Origin の検査の抜けにあたる。どれも「境界の一方だけを直した」ことで起きている。**修正の diff を読むときは、同じ値を読む別の入口 (クエリ、別のルート、別の正規化) がないかを横に広げて探す**のが近道。
- middie は 9.3.7 の修正が 1 日で回避された。Express 互換の層 (`@fastify/express`、`@fastify/middie`) のほか、**Hono、Koa の互換ミドルウェア、NestJS の Fastify アダプター**のような、「別のルーターの上でミドルウェアのパスを自前で照合する」実装にも、同じ型があるはずだ。空のパラメータ、`*` で始まるターゲット、`%25` の二重デコード、`\` の扱いの 4 つを試すと効率がよい。
- isomorphic-git の `.git::$INDEX_ALLOCATION` は、ネイティブの Git が 2014 年以来たびたび直してきた NTFS の別名の問題 (背景) を、**別言語の独立した実装**がまだ持っていたケース。go-git、JGit、libgit2 のバインディング、dulwich など、他の純粋な実装でも、ツリーのエントリの検証が同じ別名を拒否しているかを確かめる価値がある。
- goproxy は「`hash.Sum(nil)` のつもりで `hash.Sum(data)` を使った」型の暗号 API の誤用で、MITM のプロキシ (診断で使う側の道具) の鍵が予測できた。**自前の MITM の道具や、Go で書かれた検査プロキシ**を使っている場合は、版を確かめたい。
- 優先して見る順は、① MONAI Label (悪用中で修正版なし、AI / ML のサーバーの棚卸し)、② fastify 系 (利用者が多く PR:N)、③ Mitel MiCollab (CVSS 10、PoC の公開に備える)、④ GPGME (静的リンクの洗い出し)。
