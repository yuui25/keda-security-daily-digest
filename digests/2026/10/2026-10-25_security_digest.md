### Linux カーネル ZDI-CAN-33367 — Dirty Frag の修正から漏れていた 7 本目の経路。root を取る PoC が、CVE も本流の修正もない状態で公開された

- **概要 (事実)**: ZDI は 10/20〜21 に Linux カーネルの脆弱性 5 件 (と ConnMan の 1 件) を報告し、公開メーリングリストにも CC した。このうち ZDI-CAN-33367 (`skb_zerocopy()`、CVSS 7.8) は、報告に付いていた PoC を TuxCare が再現し、最新の Ubuntu・Debian・AlmaLinux で一般ユーザーから root を取れることを確かめた。Sysdig が 10/24 に整理した時点で、CVE は未採番。修正パッチ「net: skbuff: propagate shared-frag marker in skb_zerocopy()」は 10/22 に netdev に v2 が投稿されて Eric Dumazet のレビューを受け、stable 向けのタグも付いたが、まだマージされていない。実際の悪用は報告されていない。
- **技術的な中身**: Dirty Frag (CVE-2026-43284) の型である。IPsec ESP の処理が、ページキャッシュに属するページの上で「その場で」復号すると、一般ユーザーが読むことしかできないファイル (setuid バイナリや `/etc/passwd`) のキャッシュ上の内容を書き換えられる。Dirty Frag の修正は「共有されたフラグメント」に印 (フラグ) を付け、ESP は印を見たら先にコピーしてから復号するようにした。ZDI-CAN-33367 は、`skb_zerocopy()` がページを新しい sk_buff に移すときにこの印を引き継がないため、ESP が印を見られずにその場で復号してしまう、という修正の漏れである。問題のコードは 3.14 からある。PoC は、非特権のユーザー名前空間と、いくつかのネットワーク系モジュール (nlmon、nfnetlink_queue / nft_queue、cls_u32、act_pedit、act_mirred、esp4) を使い、KASLR のリークは要らない。
- **背景・経緯 (過去の事象の引用)**: 2026 年 5 月に、ページキャッシュを書き換える LPE が続けて公表された。Copy Fail (CVE-2026-31431、Microsoft が 5/1 に解説)、Dirty Frag (CVE-2026-43284 / 43500、5/7)、Fragnesia (CVE-2026-46300、5/13) である。Sysdig によると、それ以降もカーネルの CVE チームは、ほかの経路で印が失われる修正漏れを 6 件採番している (CVE-2026-43503、46300、53363、64566、80977、90049)。CVE-2026-90049 は同じ `skb_zerocopy()` の別のエラー経路のバグで、これを直したカーネルでも ZDI-CAN-33367 は直っていない。なお、同じ一連の報告の KSMBD の 2 件 (ZDI-CAN-33774 / 33549) は 10/23 号で既報。
- **なぜ今これが重要か (評価)**: 3 つの条件がそろっている。(1) 動く root の PoC が公開済み、(2) 主要ディストリの標準カーネルが対象、(3) CVE がないので、CVE ベースの脆弱性スキャナや SBOM の照合では見つからない。「印を付けて回る」型の修正は、ページを動かすすべてのコードが印を引き継ぐことに依存しているので、今後も同じ型の漏れが出続けると考えるのが自然である。ペンテストや診断の立場では、Web アプリで足場を得たあとの権限昇格の候補として、当面は「パッチ済みのカーネル」の上でも成立しうる。CI ランナー、共有の開発サーバー、rootless コンテナを使う基盤が最も影響を受ける。Sysdig によると、Ubuntu の AppArmor による名前空間の制限は、コンテナランチャーのパッケージの AppArmor プロファイル経由で回避された。
- **読者が今日できること**:
  - 自分の管理する Linux (特に一般ユーザーやコンテナのコードが動くホスト) で、非特権のユーザー名前空間が必要かを見直す。不要なら `kernel.unprivileged_userns_clone=0` (Debian 系) や `user.max_user_namespaces=0` で塞ぐ (TuxCare は PoC に対する効果をまだ検証していないと注記)。rootless コンテナやブラウザのサンドボックスが壊れる可能性があるので、ホストの役割ごとに判断する。
  - PoC が使うモジュールのうち、使っていない `nlmon` と `act_pedit` を `/etc/modprobe.d/` の `install <mod> /bin/false` で読み込めなくする (PoC は止まるが、すべての経路が閉じるとは限らない)。Kubernetes では、Pod の seccomp を `RuntimeDefault` にして、コンテナからの `unshare(CLONE_NEWUSER)` を止める (既定は Unconfined)。
  - 検知: 1 つの非特権プロセスが「user / net 名前空間の作成 → nlmon インターフェースの作成 → XFRM state の登録 → nftables の NFQUEUE ルール → tc pedit + redirect → 127.0.0.1 への splice()」を続けて行うのは正規の動きではない。auditd / Falco / EDR でこの並びを相関させるルールを入れる。修正については、netdev のパッチのマージと各ディストリのカーネル更新を追う (CVE が採番されたら追跡対象に加える)。

### 今日の CVE 所感
- **「チェックした値」と「使う値」の不一致**が多かった。Livewire (キー名で認可、位置で実行)、Craft Commerce Mollie (取引ハッシュと決済 ID を別々に信頼)、Echo (Upgrade の成否を確かめずにトンネル化)、nodemailer (ヘッダー上の宛先と配送先のずれ) はすべてこの型。ソースコード診断では「認可・検証に渡した値」と「実処理に渡す値」を同じ変数から取っているかを追うと見つけやすい。
- **水平展開の候補**: Echo 型の「WebSocket Upgrade の失敗後もトンネルを維持」は、Go / Node / Python の自作リバースプロキシやミドルウェア (http-proxy 系) で同じ実装を探す価値がある。Zephyr の WireGuard は「認証前のパケットでエンドポイントを更新」で、組み込み向けの独自 WireGuard 実装に共通しうる。決済 Webhook の「ID の対応を確かめない」は、Stripe / PAY.JP など他の決済連携プラグインでも定番の確認点。

- **何が起きたか**: GMO インターネットグループは 10/24 に、お名前.com デスクトップクラウドの事案を「能動的サイバー防御の発動第 1 号」と位置づけ、国が主導して攻撃基盤を追跡・遮断・無力化するよう、政府の関係機関に要請したと発表した。共同通信によると、GMO は、発動されれば 10/1 の関連法施行後で初めての案件になると説明している。

#### [2026-10-24] Zenn「サポート切れの PHP 7.4、php2shell で青ざめたら実は直っていた話」— バージョン番号だけでは「危ない」とも「大丈夫」とも判断できない
- **何が起きたか**: hirosy 氏が公開した。管理しているサーバーで `php -v` が 7.4.33 と出たが、実際は Plesk が 10/21 にビルドし直したパッケージだった。PHP のセキュリティチームが 7.4〜8.1 向けに出した最小限の修正を取り込んでおり、番号は 7.4.33 のまま中身だけ直っていた。確かめ方を 3 つ挙げている。(1) パッケージのビルド日 (Plesk なら `261021` が入っているか、`rpm -q` / `dpkg -l` で調べる)。(2) PHP-FPM を再起動したか (`/proc/<pid>/exe` に `(deleted)` が出たら、古いバイナリがまだ動いている)。(3) mod_php で動かしていないか。EOL 版の修正は、メモリの上限を超えた時点で処理を打ち切る作りのため、更新後に 502 エラーが出ることがあるとも書いている。
- **なぜ重要か**: 脆弱性診断の現場で、バナーやバージョン番号だけで判定すると、誤検知 (バックポートで直っている) と見逃し (更新したが再起動していない) の両方が起きる典型例である。PHP2Shell のように、ディストリビューションやホスティング事業者が独自に修正を当てる脆弱性 (さくらやロリポップも EOL 版に修正を適用) では、報告書に「バージョン番号による推定」と明記し、パッケージのビルド日と動いているプロセスまで確認する手順を標準にしたい。
